# Dynatrace

The Dynatrace backend is **ingest-only**, and sends logs to [Dynatrace](https://www.dynatrace.com) via the [Log Monitoring API v2](https://docs.dynatrace.com/docs/dynatrace-api/environment-api/log-monitoring-v2/post-ingest-logs).

## Behaviour and configurations

### Configuration

The backend can be configured with the following options:

- `:url` (string, required) - The Dynatrace environment URL. Logs are sent to `/api/v2/logs/ingest` under this URL.
- `:api_token` (string, required) - An access token with the `logs.ingest` scope.

### Obtaining the configuration values

1. In Dynatrace, open **Access Tokens** and select **Generate new token**.
2. Name the token, add the **Ingest logs** (`logs.ingest`) scope, and generate it. Copy the token value into `:api_token`.
3. The environment URL is `https://<environment-id>.live.dynatrace.com` for Dynatrace SaaS, where `<environment-id>` is the identifier in your Dynatrace URL. When sending through an Environment or Cluster ActiveGate, use `https://<activegate-host>:9999/e/<environment-id>`.

### Implementation Details

- Log events are sent as a JSON array of log records. Each record holds the log event body as attributes, with the log event message under `content`, the log event timestamp as an ISO 8601 string under `timestamp`, and the Logflare source name under `log.source`.
- Dynatrace detects the log level from top-level attributes such as `level` or `severity`.
- How nested objects are stored depends on the data model of your Dynatrace environment.
- Authentication uses the `Authorization: Api-Token <token>` header.
- Testing the connection sends an empty payload. Dynatrace checks the token before the payload, so an accepted payload or an invalid input error both verify reachability and the token.
- URLs pointing at private or reserved IP addresses are rejected.

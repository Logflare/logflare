# VictoriaMetrics

The VictoriaMetrics backend is **ingest-only**, and sends metric events to [VictoriaMetrics](https://victoriametrics.com) using the Prometheus remote write protocol (v1).

## Behaviour and configurations

### Configuration

The backend can be configured with the following options:

- `url` (`string`, required) - The remote write endpoint, such as `https://victoriametrics.example.com/api/v1/write`. Private and reserved addresses are rejected.
- `username` and `password` (`string`, optional) - Basic auth credentials. Both must be provided together.
- `headers` (`map`, optional) - Extra headers attached to each request. Credential headers such as `authorization` are redacted when the backend is read back.
- `labels` (`map`, optional) - Static labels added to metric time series, excluding `target_info`. These take precedence over event attributes with the same name. Labels can be set through the management API.

Stored credentials are only sent to the host they were entered for. Changing the URL to another host clears the password and credential headers, so they need to be entered again.

### Implementation Details

Implementation is based on the [webhook backend](/backends/webhook).

- Only metric events are sent: OpenTelemetry metrics, and JSON events that Logflare classifies as metrics.
- Gauges and sums are sent as a single series. Histograms are sent as `_count`, `_sum` (when the data point has a sum) and cumulative `_bucket` series with an `le` label, formatted as a plain decimal such as `0.005` or `1000`. The `+Inf` bucket is the data point's count.
- Sums and histograms must use cumulative temporality. Remote write has no way to represent delta temporality, so those data points are dropped.
- NaN and infinite values are sent as such.
- Log and trace events, exponential histograms, delta data points and malformed data points (for example, bucket counts that do not match the bounds) are dropped and counted in the `logflare.backends.victoria_metrics.drop` metric, tagged by reason. A batch that drops metric data points also logs a warning.
- Payloads are Protobuf-encoded and snappy-compressed, and batched with a maximum of 250 events per request.

### Labels

- `source` is set to the source name. Renaming a source starts new series under the new name.
- `job` is set from the `service.name` resource attribute, prefixed with `service.namespace/` when present, and `instance` from `service.instance.id`. A resource without an instance ID uses an empty `instance` value. Independent producers must supply distinct service identities; other resource attributes do not distinguish their metric series.
- `otel_scope_name`, `otel_scope_version`, and `otel_scope_schema_url` contain the corresponding instrumentation scope fields when present. Scope attributes become `otel_scope_<attribute>` labels, following the [OpenTelemetry scope conversion rules](https://opentelemetry.io/docs/specs/otel/compatibility/prometheus_and_openmetrics/#instrumentation-scope-1). Arrays and maps are JSON-encoded. Scope attributes that would collide with the three scope metadata labels are omitted; other scope label collisions join the values with `;` in original-key order.
- Data point attributes with non-empty string, number or boolean values become labels; list and map values are skipped. Logflare normalizes attribute keys at ingest, so an attribute such as `http.route` is sent as the `_http_route` label.
- Metric and label names are converted into valid Prometheus identifiers, so a metric named `http.server.duration` becomes `http_server_duration`.
- The labels the backend sets (`__name__`, `le`, `source`, `job` and `instance`) always win. An attribute or configured label with one of those names is kept as `exported_<name>`, for example `exported_job`.

Resource attributes are exported on a separate `target_info` series with value `1`, following the [OpenTelemetry resource mapping](https://opentelemetry.io/docs/specs/otel/compatibility/prometheus_and_openmetrics/#resource-attributes-1). Its labels contain the resource attributes plus `job` and `instance`, without source, configured, data point, or scope labels. Arrays and maps are JSON-encoded. No `target_info` is emitted for an empty resource or a resource with neither a service name nor an instance ID.

Each batch emits at most one `target_info` sample per `job`/`instance` pair, using the resource from the latest accepted data point. Conflicting resources at the same timestamp are resolved deterministically by the sorted labels. Resource attributes are not automatically promoted onto metric series; use `job` and `instance` to join with `target_info` when querying.

When resource metadata changes across batches, earlier `target_info` series may remain query-visible during the receiver's lookback window. Queries must select the latest metadata for each target before joining; this adaptor does not send stale markers for earlier metadata series.

These mappings use the data available after Logflare's ingestion normalization, which may already normalize attribute keys or remove empty values. For example, the resource attribute `host.name` is available as `_host_name` on `target_info`. The backend cannot recover distinctions removed before it receives an event.
